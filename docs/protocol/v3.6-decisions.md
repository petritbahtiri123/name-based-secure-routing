# NBSR Protocol Vision V3.6 decision record

**Status:** Approved architecture direction with unresolved wire and runtime
gates

**Date:** 2026-07-28

**Authority:** [NBSR Protocol Vision V3.6](../architecture/NBSR_Protocol_Vision_V3.6.md)

**Runtime authorization:** None. Phase C authorization is limited to the
internal Derived OriginSet model and focused tests.

## D7 approved

The [OriginSet compatibility and authority decision](originset-compatibility-authority-decision.md)
freezes:

- an internal-only Derived OriginSet for WP2/WP3;
- a separately versioned Core v0.2 native OriginSet;
- mode-specific issuer authority and caller-supplied trust contexts;
- an explicit mapping from frozen D6 publication policy to V3.6 lifecycle
  modes;
- fail-closed generation, sequence, equivocation, rollback, and tombstone
  behavior; and
- COSE Sign1 as the future native-wrapper direction.

D7-1 through D7-5 were approved by the human protocol owner on 2026-07-28.
The approval allocates no wire values. It authorizes only the bounded internal
Derived OriginSet model in Phase C; all adapters and runtime behavior remain
gated.

## WP3 single-service transport proposal prepared

The
[WP3 single-service transport decision](wp3-single-service-transport-decision.md)
proposes `aioquic` for the Python prototype only, exact ALPN
`nbsr-quic-1`, private-lab-CA mutual TLS 1.3, an edge-scoped Transport Session
reuse key, and native reliable QUIC streams for the initial TCP profile.

The review found an application-stream binding wire gap: Core v0.1 has frozen
`STREAM_OPEN`, `STREAM_ACCEPT`, and `STREAM_REJECT` codes but no frozen
message-body schema binding QUIC stream ID, Service Channel, service,
RouteGrant, policy, and replay context. The proposal allocates no values and
authorizes no transport runtime.

## Approved V3.6 architecture

The following concepts are approved for forward-looking architecture and
test-plan work:

1. **Resolver-first:** every successful resolution through an upgraded NBSR
   network returns a scoped synthetic IP. Origin addresses remain internal and
   direct client fallback is forbidden.
2. **Identity separation:** Service Identity, Synthetic IP, Origin Endpoint,
   Source Edge, Destination Edge, and connector/service target are separate
   concepts. Service Identity is never an IP.
3. **Layering:** `Transport Session -> Route Context / Service Channel ->
   Application Stream`.
4. **Session reuse, service isolation:** compatible authenticated transport may
   be reused, but every Service Channel has independent authorization,
   service/name binding, revocation, quotas, audit attribution, failure
   containment, and security context.
5. **Cryptographic separation invariant:** every Service Channel has an
   independent cryptographic or transcript-bound context. No exact derivation
   algorithm is approved by this statement.
6. **Origin lifecycle:** the migration direction is `LEGACY_DNS`, `HYBRID`,
   then `NBSR_NATIVE`; legacy DNS is reachability only.
7. **Origin precedence:** valid signed native OriginSet, valid delegated
   Destination Edge/connector metadata, constrained legacy DNS, then fail
   closed.
8. **Safe replacement:** validate new endpoints before use, direct new channels
   to valid replacements, and drain or explicitly invalidate old endpoints.
9. **Mobility:** path changes do not create identity or authorization.
   Migration, resumption, failover, and handover preserve every existing
   security binding.
10. **Application-protocol boundary:** NBSR owns secure routing, not user login,
    OAuth, HTTP semantics, database semantics, or application transactions.

These are architectural decisions, not new Core v0.1 wire allocations.

## Frozen Core v0.1 decisions preserved

D1-D6 remain approved and unchanged. In particular:

- the complete mapping of 17 message codes remains unchanged;
- the complete mapping of 19 error codes remains unchanged;
- the six D6 numeric object schemas remain unchanged;
- deterministic CBOR and COSE wrapper rules remain unchanged;
- ServiceRecord, RouteGrant, and Revocation remain the only D6 object-level
  COSE Sign1 payloads;
- revocation `expires_at`, `target_sequence`, and issuer-generation tombstone
  behavior remain unchanged; and
- the frozen Resolution, Tunnel, Stream, and Connector state registries and
  transitions remain unchanged.

The V3.6 conceptual publication modes `LEGACY_DNS`, `HYBRID`, and
`NBSR_NATIVE` do not replace or alias the D6 ServiceRecord `publication_mode`
values `legacy`, `dual-published`, `nbsr-preferred`, and `nbsr-secure-only`.
D7-3 defines their policy relationship without changing either vocabulary.

## Superseded forward-looking decisions

| Historical statement | Superseding V3.6 decision | Impact |
|---|---|---|
| Vision V3 allowed a legacy name to return ordinary origin A/AAAA data to the client | Every successful upgraded-network resolution returns a synthetic IP | WP2 must convert legacy reachability into an internal temporary OriginSet and never expose it |
| Vision V3 terminology separated legacy resolution from route state | Every successful result creates or retrieves synthetic mapping; secure routing begins when the client connects | Documentation and tests use a single client-visible outcome |
| Earlier tunnel descriptions did not distinguish shared transport from service authorization | Session reuse, service isolation | WP3 must not block reuse; WP4 owns reusable multi-service channels |
| Earlier origin handling described connector or DNS reachability without a complete publication lifecycle | Three migration modes, precedence, rollback protection, and safe drain | WP2, WP3, WP4, and WP6 gain explicit origin work |
| Earlier mobility text focused on a tunnel state | Continuity must preserve channel-, gateway-, client-, service-, policy-, expiry-, revocation-, and replay-binding | Migration/resumption/handover require dedicated gates and conformance plans |

The historical documents remain available with their original evidence and
dates. Supersession applies only to forward-looking claims.

No backward-compatible extension is approved by this matrix. It identifies the
classification route that a future proposal may take. Any direct modification
of a frozen D1-D6 value is an **incompatible change** requiring explicit human
approval and a versioning decision.

## Conflicts requiring human resolution

1. **Service Channel registry:** decide whether existing route/stream messages
   can carry the model without ambiguity or whether Core v0.2 codes are needed.
2. **OriginSet wire authority:** D7 freezes issuer classes, delegation, caller
   trust context, and future COSE Sign1 direction; exact schema, `kid` binding,
   emergency revocation, and transparency remain unresolved.
3. **Drain semantics:** decide maximum lifetime and the conditions that force
   immediate invalidation instead of graceful completion.

Until approved, these conflicts block the relevant runtime or wire task, not
the documentation architecture.

18. IP profile selection, selectors, MTU, and fragmentation behavior;
19. Web PKI requirement level for LEGACY_DNS and HYBRID origin candidates;

22. HA staleness limits and fail-closed read requirements; and
23. approved interception mechanisms and bypass evidence per platform.

No item in this list is implicitly approved.

The Phase D prototype outage policy is approved: timeout/SERVFAIL may use a
previously validated Derived OriginSet through a configurable 300-second
last-known-good grace, while authenticated negative, DNSSEC bogus/downgrade,
policy failure, rollback, and equivocation invalidate new use immediately.
Production values and the health-check/Web PKI trust model remain pending.
