# KAR genesis semantic prerequisite — design only

Decision ID: `KAR-GENESIS-SEMANTICS-01`. This record authorizes no implementation, signing, new keys, builds, runtime configuration or live authority. The adjacent [inventory](2026-10-11-kar-genesis-design.json) pins the reviewed sources and exact fixture identities.

## Finding and proposed boundary

The reviewed retained signed packages and source recipes contain no purpose-12 KeyAuthorizationRecord (KAR) chain matching the five current normal-revocation roster keys. Their supplied public keys, purpose, lifecycle and validity remain fixture assertions. Existing purpose-3 records cannot substitute for purpose-12 authorization.

The smallest coherent next implementation proposal is a test-only, genesis-only native KAR semantic verifier under an explicitly supplied test IDENTITY_ROOT. It would reproduce the existing purpose-3 semantic recipe and reject that same authorization when purpose 12 is required. A private checked-result type would have no conversion to an Authority, admission permit, owner mutation or READY state. This is a prerequisite, not positive normal-roster integration.

## Proposed semantic contract

Reuse the existing native exact COSE verifier and canonical decoding bounds. Require Ed25519, the exact protected kid and attached canonical payload, empty unprotected headers and external AAD, and existing size/signature bounds. Signature success alone is insufficient.

Validate KAR object type 2/version 1 and the existing required/allowed field set. Require exact integer/boolean types, bounded timestamps, operator length 32, child kid length 1–64 and public key length 32. Require generation/sequence 1/1 and absence of predecessor and recovery-transition fields. Reject rotation/recovery rather than inventing lineage state. No durable or in-memory update floor is introduced by this slice.

Require a well-formed, ACTIVE, unrevoked, currently valid supplied root with purpose IDENTITY_ROOT (1). Bind field 32 to its operator and field 37 exactly to its class-1 operator/kid reference. Require the child purpose to equal the explicit requested purpose; no default-purpose fallback. A usable child must be ACTIVE, unrevoked and valid at the evaluation time, using existing inclusive validity semantics. Root and child checks both apply, including exact start and expiry boundaries. Match the caller's explicitly supplied expected child identity and payload rather than accepting a different signed key as the requested key.

Field 3 receives existing schema validation. The Python verifier does not independently join field 3 to the root as it does field 37; this proposal does not silently add a global contract rule. The selected positive recipe has matching fields 3 and 37. Historical issuer mismatches must not be described as independently rejected by Python unless a focused check establishes that result.

KAR has no service-scope field. It authorizes a key purpose, not class-4 roster membership, organizational independence, quorum membership, service scope or ownership. Contextual scope joins remain separate. The only trust source is the explicitly pinned supplied test root; no root discovery, production trust store or genesis-provenance claim is added.

| Schema/state | Missing/unknown invalid fields, bool-as-integer, invalid sizes/times, inconsistent revocation marker, inactive/revoked child |
| Validity | Both exact starts accepted where otherwise valid; both exact expiries accepted where otherwise valid; either expiry + 1 rejected; disjoint retained intervals rejected |
| Lineage | Sequence 2, generation 2, predecessor/recovery fields and terminal/revoked use rejected; no inferred transition or reused terminal key |
| Integration | Every rejection leaves caller state untouched; no checked result grants admission, mutates owner, advances production floors or sets READY |

New malformed signed payload cases would require separately authorized fixture materialization. Existing historical bytes are never repaired to manufacture positive cases.

## Assertions and remaining decision

The proposed slice replaces **no current normal-roster assertion**. It would establish a native test-only purpose-3 KAR semantic result relative to a supplied test root. A later slice could derive normal keys' signed purpose/lifecycle/validity binding only after approving new purpose-12 fixture records and explicit root to operator to operational-key mappings for all five roster members. Existing public deterministic keys may be reused, but these records would be new fixtures. Do not implicitly collapse five independent operators into one root or infer mappings from synthetic IDs.

Production genesis provenance, current governing configuration, root/key rotation and recovery, authenticated revocation delivery, durable rollback floors, real timers, live admission and Stage 3 closure remain unsupported. Existing connected-owner evidence and its SuppliedTestTrust boundary remain unchanged.

Decision for the parent/user: approve this isolated genesis-only prerequisite, or first approve the exact five purpose-12 fixture mappings and new signed fixture scope. The former is the smallest coherent implementation; it does not by itself authorize connecting the normal roster.
