# Offline Windows ownership diagnosis

No new runtime/test changes or live commands. Six pre-existing dirty paths preserved. No new tests/lint needed because no patch was made; previous instrumentation checkpoint remains 66 passing tests and Ruff, not a new run.

Identity: WindowsOwner.process is PROCESS_INFORMATION.hProcess returned by CreateProcessW for sys.executable -B -m scripts.performance.windows_docker_provisioning --command request. It identifies that newly created helper executable process, possibly a launcher depending on sys.executable, not its Docker descendant. The actual helper PID was not retained. Worker Popen returned Docker CLI PID 16380; no code substitutes that child handle for the owner's process handle. AssignProcessToJobObject uses the original helper handle before ResumeThread. Handles remain open until explicit successful reaping, so this path does not intentionally reopen by PID or reuse a stale closed handle.

Accounting: ActiveProcesses comes from QueryInformationJobObject information class1. It is a sampled Job accounting count, not a list of identities, proof that the separately held helper handle is signalled, or proof about daemon/container ownership. Its documented definition does not supply an atomic joint process/Job snapshot. Four observed processes cannot be identified individually from a count. No breakaway flag or inherited handles were requested; that source fact is not independent runtime membership verification.

Termination: TerminateJobObject is documented as TerminateProcess for each associated process. TerminateProcess from another process is asynchronous and requires a process wait to establish completion; pending I/O can delay exit. The success return therefore does not authorize closing ownership on the basis of Job count alone. Pending I/O is a possible explanation, not an observed fact here.

Why reordering was insufficient: the old deterministic test demonstrated a stale leader-first snapshot combined with a newer Job count. The live source instead sampled Job first and still returned (None,0). Thus that specific read-order interleaving cannot by itself explain the latest outcome. Backend None means WaitForSingleObject returned WAIT_TIMEOUT under the checked source, but raw API return/timing/handle identity was not logged. About1.23ms after termination returned, the aggregate backend result was recorded; no subsequent post-termination observation exists because WindowsOwner raised. We cannot establish how long that state persisted or whether the remaining ~2s cleanup reserve would have sufficed.

Missing observations: original helper PID plus handle-to-PID validation; exact Job membership/identity evidence for the helper; per-call timestamps and raw results for Job query and zero-time process wait; repeated observations on those same retained handles through the existing deadline after termination. Invalid native API returns must remain errors. Diagnostic continuation must not permit new work, clear ownership, infer zeroes, or reset deadlines. A real native observation of those fields requires separate live approval and an independently reviewed bounded diagnostic path. Daemon receipt/internal-stage evidence is separately missing for the primary Docker create delay.

Decision: no further behavior patch is justified by this trace alone. Preserve conservative rejection and all historical UNCONFIRMED outcomes. No Docker command, container, process probe, build, download, credential action, commit or push in this investigation.
