# NBSR V3.6 Protocol Roadmap

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:executing-plans` only after the relevant phase has explicit
> human approval. Steps use checkbox syntax for later tracking.

**Goal:** Sequence V3.6 decisions, internal models, compatibility adapters,
service-isolated transport, origin updates, and continuity without changing
frozen Core v0.1 contracts prematurely.

**Architecture:** Preserve D1-D6 as the Core v0.1 byte contract. Introduce
V3.6 concepts first as reviewed documentation and bounded internal models,
then cross a wire or runtime boundary only after the listed human gate.

**Tech stack:** Documentation, Python protocol package, deterministic local
fixtures, later QUIC/TLS 1.3 profile, and repository conformance tests.

## Global constraints

- Do not implement runtime behavior from this plan without approval.
- Do not change D1-D6, 17 message codes, 19 error codes, frozen field mappings,
  COSE wrappers, `kid` bindings, or state transitions silently.
- Do not expose origin data to clients, fixtures, ordinary logs, or errors.
- Do not use public DNS or Internet services in deterministic tests.
- Do not begin a later phase before the prior phase's evidence and approval
  gate pass.
- Do not merge to `main` or modify the Build Week submission branch as part of
  this roadmap.

## Work-package reconciliation

## WP2 - Name Node and legacy reachability adapter

**Reuse:** `dnslib` is present for current DNS parsing; use standards-conformant
recursive DNS, A/AAAA/CNAME, RFC 2308 negative caching, RFC 9460 SVCB/HTTPS,
DNSSEC validation through a reviewed resolver/library, and Web PKI validation.

**NBSR custom code:** constrained origin discovery adapter, internal
`publication_mode`, deterministic temporary Derived OriginSet construction,
independent discovery caching, stable Synthetic IP mappings across refresh,
endpoint policy, rollback/equivocation rejection, and fail-closed behavior.

WP2 does not serialize OriginSet or allocate a message code. It must prove that
every successful resolution returns a Synthetic IP and that DNS TTL is not an
authorization lifetime.

**Human gates:** DNSSEC requirement/downgrade policy, legacy Web PKI requirement
level, DNS outage/last-known-good policy, production synthetic prefix, and
OriginSet internal-model approval.

## WP3 - First transport and validated final segment

**Reuse:** choose a reviewed QUIC v1/TLS 1.3 implementation for Connection IDs,
streams, flow control, congestion control, loss recovery, path validation,
NAT rebinding, close, key update, Retry, anti-amplification, and DPLPMTUD.

**NBSR custom code:** model explicit Transport Session identity and bind the
existing Route Context to one Service Channel; perform source/destination
admission; select the final segment only from a validated OriginSet; bind each
TCP Application Stream to the authorized service context.

WP3 must prove source and destination admission, Service Identity separation
from Origin Endpoint, and zero origin disclosure. A single-service vertical
slice is acceptable, but its interfaces must not assume one service per
transport forever.

**Human gates:** QUIC library, ALPN and certificate/trust profile, transport
reuse key, application-stream preface or CONNECT choice, and provisional
resource/time limits.

## WP4 - Reusable multi-service transport and lifecycle

**Reuse:** QUIC multiplexing and flow control, TLS 1.3 exporters/channel
binding, standard fair schedulers/token buckets, CONNECT-UDP plus HTTP
Datagrams/Capsules or QUIC DATAGRAM if UDP is approved.

**NBSR custom code:** reusable multi-service Transport Sessions, Service
Channel lifecycle, per-service authorization/revocation/quotas/audit,
independent exporter-bound context, failure containment, graceful origin
change, and approved migration/resumption semantics.

WP4 cannot begin the service-channel wire or key schedule until those gates are
approved.

**Human gates:** Service Channel wire representation, RouteGrant reuse,
exporter derivation and vectors, exact quotas/timeouts, UDP framing, drain
maximum, and same-edge/cross-edge resume.

## WP5 - Gateway packaging and policy conformance

**Reuse:** nftables/TPROXY, policy routing, TUN, eBPF and local DNS interception
on Linux/OpenWrt; WFP and resolver integration on Windows; existing OS
least-privilege, signing, service, and firewall mechanisms.

**NBSR custom code:** synthetic-prefix correlation, capture self-test/bypass
detection, cross-service isolation policy, denial/revocation behavior,
compatibility fallback constraints, origin-leak checks, and fair-share/noisy-
neighbor enforcement. Packaging keeps the Name/Resolution and Secure
Route/Tunnel planes isolated.

**Human gates:** platform-specific interception mechanism, signed Windows
component requirements, production prefixes, policy defaults, and leakage/
operational evidence.

## WP6 - Replicated origin and continuity state

**Reuse:** etcd/Raft, PostgreSQL replication, signed snapshots, replicated
logs, or another proven storage/consensus system. Do not design an NBSR
database protocol.

**NBSR custom correctness:** replicate accepted OriginSet generation,
sequence, digest, revocation, replay, policy, and tombstone state; reject stale,
replayed, equivocated, or split-brain updates; add bounded failover,
Destination Edge handover, cross-replica resumption, and drain behavior that
never resurrects a revoked Service Channel or grant.

**Human gates:** OriginSet authority/wire, publisher conflict policy, HA
staleness, fail-closed read rules, cross-edge resume, handover authority/proof,
and bounded failover/drain limits.

## Phase sequence

### Phase A - Documentation reconciliation and decisions

**Prerequisites:** Supplied V3.6 source and approved D1-D6.

**Expected files:** `docs/architecture/*V3.6*`,
`docs/protocol/v3.6-*`, threat model, status, terminology, and this roadmap.

**Tests:** Documentation structure, current pointer, invariant, link, frozen
registry, and no-runtime-diff checks.

**Human approval gate:** Approve the reconciled V3.6 architecture, conflict
list, compatibility matrix, and pending gates.

**Abort criteria:** A historical record would need deletion, a frozen decision
would change, or runtime code is required for consistency.

### Phase B - OriginSet compatibility decision

**Prerequisites:** Phase A approval.

**Status:** D7-1 through D7-5 approved on 2026-07-28. Phase B complete.

**Expected files:** Decision amendment defining internal/extension/Core v0.2
placement, issuer authority, wrapper, trust context, mode mapping, rollback,
equivocation, and drain policy.

**Tests:** Decision-document completeness and unchanged D1-D6 registry/schema
tests.

**Human approval gate:** Review D7-1 through D7-5. Approve exact placement,
authority model, mode mapping, rollback/equivocation rules, and future wrapper
direction separately. Any wire form requires its own numeric schema review.

**Abort criteria:** Issuer authority, signing wrapper, publication-mode
mapping, or compatibility classification remains ambiguous.

### Phase C - Internal models and documentation tests

**Prerequisites:** Phase B approval for internal-model scope; no wire allocation
required.

**Status:** Phase C approved and complete. The minimal internal Derived
OriginSet model remains wire-neutral. Service Channel modeling is deferred and
remains separately gated.

**Expected files:** `nbsr/originset.py`, `tests/test_originset.py`, and D7
status documentation; no runtime integration.

**Tests:** Immutability, strict bounds/types, generation/sequence rollback,
same-sequence equivocation, issuer context, privacy, and deterministic fixtures.

**Human approval gate:** Approve model boundaries and confirm zero frozen-wire
impact before adapters consume them.

**Abort criteria:** A model requires a new Core key/code/state or cannot be
kept separate from D6 payloads.

### Phase D - Legacy DNS-backed OriginSet

**Prerequisites:** Phase C model approval and WP2 runtime approval.

**Status:** Phase D implementation approved and complete. The isolated adapter
supports bounded last-known-good behavior for temporary failure. NameRelay
integration remains gated.

**Expected files:** `nbsr/legacy_origin.py`, focused deterministic tests,
independent discovery cache, temporary OriginSet conversion, and approved
outage-profile documentation.

**Tests:** Synthetic response always, origin never returned, no direct
fallback, stable mapping across refresh, DNS TTL separation, new-before-old
validation, stale/equivocated update rejection, and bounded failure.

**Human approval gate:** Review WP2 security boundary and observed tests before
any native publication work.

**Abort criteria:** Public DNS is required in tests, DNS data grants
authorization, or origin data reaches client-visible state.

### Phase E - Single-service channel over existing transport

**Prerequisites:** Approved WP3 design and a validated internal OriginSet.

**Status:** Phase E transport, STREAM, HELLO, ROUTE, and D8 version direction
approved. The
[written D8 version-selection record](../../protocol/core-v0.2-version-negotiation-decision.md)
and deterministic-vector design were approved on 2026-07-29. The exact public
fixture and generated-byte review remain required, and runtime remains blocked
until the vectors receive separate approval and a TDD implementation plan is
reviewed.

**Expected files:** Transport Session identity, one Route Context / Service
Channel binding, final-segment selector, and conformance fixtures.

**Tests:** Independent source/destination admission, service/name/grant/policy
binding, invalid origin rejection, and origin concealment.

**Human approval gate:** Approve the single-service boundary and confirm it
does not encode one-service-per-session assumptions.

**Abort criteria:** Service authorization is attached only to the transport
session or final-segment selection bypasses OriginSet validation.

### Phase F - Multi-service Transport Session reuse

**Prerequisites:** Approved Service Channel wire representation,
transport-session scope/reuse key, and Route Grant reuse policy.

**Expected files:** Multi-channel transport/session manager, independent
channel lifecycle, quotas, audit, and failure containment tests.

**Tests:** Two services share one compatible session with separate
authorization; grant A cannot open B; channel failure and starvation are
contained.

**Human approval gate:** Approve interoperability bytes and cross-service
isolation evidence.

**Abort criteria:** Authorization, quotas, audit, or revocation collapses to
session scope without an explicit session-wide policy.

### Phase G - Per-service cryptographic separation and revocation

**Prerequisites:** Approved channel derivation/exporter schedule and
cross-language vectors.

**Expected files:** Channel key/context derivation, rekey, revocation binding,
test vectors, and verifier integration.

**Tests:** Context changes with service/route/channel/grant/policy; confused
context and replay fail; revocation cannot revive after resume/migration.

**Human approval gate:** Cryptographic review and independent vector
verification.

**Abort criteria:** Key separation is library-default behavior, binding inputs
are ambiguous, or vectors are not cross-language reproducible.

### Phase H - Native origin update and graceful drain

**Prerequisites:** Approved OriginSet wire/wrapper, update messages, issuer
authority, health-check trust, and drain maximum.

**Expected files:** Publisher/verifier, update handler, origin selector,
health-check boundary, drain controller, and replication hooks.

**Tests:** Invalid issuer/stale/equivocated/rollback updates rejected; new
origin validated before use; old streams drain or invalidate; Synthetic IP is
stable; no leak/fallback.

**Human approval gate:** Review update interoperability, failure behavior, and
operational rollback drill.

**Abort criteria:** Blind delete-and-replace, unbounded health work, split-brain
ambiguity, or client-visible origin disclosure.

### Phase I - Mobility, resumption, and handover

**Prerequisites:** Approved message types, proof format, gateway authority,
same-edge/cross-edge policy, and replicated revocation/replay state.

**Expected files:** Migration/resume/handover state handlers, replica state,
failover controller, and chaos/conformance fixtures.

**Tests:** Path/source-IP change preserves identity only; replayed proof fails;
expiry/revocation/gateway/client/service/policy binding persists; no revoked
state resurrection; bounded edge failover.

**Human approval gate:** Security review and multi-replica failure exercise.

**Abort criteria:** A grant transfers blindly, replay state is partition-unsafe,
or handover widens service authorization.

## Planned conformance catalog

- Every successful resolution returns a Synthetic IP.
- Origin IP is never returned and direct fallback is impossible.
- Legacy DNS supplies reachability only; DNS TTL is not route authorization.
- Service Identity is not an IP.
- Two services share transport only with separate authorization and context.
- Grant A cannot authorize service B.
- Service A revocation does not revive after migration, resumption, failover,
  or rollback.
- Failure of one Service Channel does not unnecessarily terminate another.
- Origin updates preserve the Synthetic IP mapping.
- Stale sequence, same-sequence different-content, and invalid issuer updates
  are rejected.
- A new origin is validated before use; old origins drain or are explicitly
  invalidated.
- Resumed state remains expiry-, revocation-, replay-, gateway-, client/device-,
  service-, and policy-bound.
- Replayed migration or resume proof is rejected.
- No unauthorized log, error, or telemetry field exposes origin data.

## Rollback principle

Every runtime phase must be independently disableable without modifying D1-D6
or deleting accepted security state. Rollback may restore the prior phase's
behavior only if it preserves universal synthetic resolution, no direct
origin fallback, revocation/tombstones, and fail-closed policy.
