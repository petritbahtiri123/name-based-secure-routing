# Core v0.2 Independent Node.js Verifier Design

**Status:** approved in principle on 2026-07-29; written specification pending
human review

**Scope:** dependency-free, second-language conformance tooling for the checked-in
Core v0.2 deterministic vector package

**Runtime authorization:** none. This design does not modify NBSR runtime code,
frozen Core v0.1 registries or schemas, Core v0.2 wire decisions, WP3 transport,
or production routing behavior.

## Objective

Create a small Node.js verifier that independently checks the Python-generated
`vectors/core-v0.2` package. Passing both implementations establishes
cross-language agreement for the approved vector package; it does not establish
production readiness or authorize WP3 runtime work.

The verifier must not import, execute, or translate the Python generator or
reference verifier. It derives its behavior from the approved protocol
documents, raw artifacts, and manifest contract.

## Language decision

Use Node.js 24 with only built-in modules.

This is the smallest viable independent implementation because Node.js 24 is
already available in the working environment and provides JSON, filesystem,
SHA-256, Ed25519 verification, and a test runner. The verifier adds no npm
dependency, package lock, network download, native addon, or generated source.

Go remains a reasonable future implementation language, but it would add a new
toolchain and CBOR module for no current interoperability benefit. Rust would
provide strong static guarantees but has the same toolchain cost and a larger
initial dependency surface. Neither is required for this gate.

## Repository layout

The implementation will create:

```text
tools/
  core-v02-node-verifier/
    README.md
    package.json
    verify.mjs
    lib/
      cbor.mjs
      crypto.mjs
      manifest.mjs
      semantics.mjs
    test/
      verifier.test.mjs
```

`package.json` contains metadata, a Node version requirement, and local
`verify`/`test` scripts only. It contains no dependencies or lifecycle scripts.

The verifier reads `vectors/core-v0.2` but never writes it. Runtime code under
`nbsr/` must not import verifier modules.

## Components

### Manifest and package verifier

`manifest.mjs` validates the closed manifest schema independently:

- exact top-level and entry keys;
- closed enum values;
- unique, sorted vector and scenario IDs;
- safe relative artifact paths with no traversal, drive, URI, or backslash;
- one manifest entry per artifact;
- no missing or unlisted artifact;
- exact byte length and lowercase SHA-256; and
- the fixed protocol, version, ALPN, and hash identifiers.

All paths are resolved beneath the caller-supplied vector root. Path containment
is checked before reading an artifact. `README.md`, `manifest.json`, and the four
documented test-key files are an explicit support-file allowlist; every other
file below `artifacts/` must be indexed exactly once by the manifest.

### Bounded deterministic CBOR

`cbor.mjs` implements only the RFC 8949 data model needed by this package:

- unsigned and negative integers;
- byte and UTF-8 text strings;
- arrays;
- maps;
- booleans and null where an approved schema permits them; and
- tag 18 only at the COSE Sign1 boundary.

It rejects indefinite lengths, non-preferred integer or length encodings,
duplicate map keys, non-bytewise map ordering, floats, unsupported tags and
simple values, invalid UTF-8, truncation, trailing bytes, booleans used as
integers, and configured resource-limit violations.

Map keys are compared by their complete deterministic encoded bytes, not by
legacy length-first ordering. The decoder exposes exact consumed source slices
so duplicate and ordering checks do not depend on JavaScript object-key
coercion.

The encoder exists only to reconstruct COSE and proof inputs and to prove that
accepted CBOR re-encodes byte-for-byte. It implements the same bounded supported
types and RFC 8949 bytewise ordering. It does not copy Python output or use a
general-purpose canonicalization shortcut.

### Cryptographic verification

`crypto.mjs` uses built-in `node:crypto`:

- SHA-256 for package and RouteGrant digests;
- Ed25519 verification for tagged COSE Sign1; and
- Ed25519 verification for the Route Open proof.

Only the checked-in public keys are read. Test seeds are neither read nor logged.
Raw 32-byte Ed25519 public keys are wrapped locally in the standard SPKI
representation required by Node. The conversion is fixed and tested.

COSE verification requires:

- tag 18;
- a four-item Sign1 array;
- protected `alg=-8`;
- protected opaque byte-string `kid` of 1 through 64 bytes;
- an empty unprotected map;
- an embedded payload;
- an empty external AAD; and
- a 64-byte Ed25519 signature.

The verifier reconstructs `Sig_structure` independently and verifies it against
the caller-selected public key. It does not trust decoded JSON metadata as a
replacement for the raw COSE bytes.

### Portable protocol semantics

`semantics.mjs` contains closed literal numeric maps for only the Core v0.2
objects and messages present in the package. Numeric keys are never derived
from JavaScript property order.

It verifies:

- protocol version and message dispatch;
- exact envelope and body keys and wire types;
- RouteGrant payload bounds and validity time;
- authorized transport and port binding;
- RouteGrant digest binding in ROUTE messages;
- Route Open transcript and proof signature;
- exact accepted versus rejected result; and
- generic close for an unknown version where D8 forbids a version-specific
  error body.

The implementation reproduces the expected outcome and symbolic error for all
32 current artifact vectors: 14 valid and 18 invalid. It also checks the eight
scenario definitions for manifest integrity and references, but it does not
reimplement the Python conformance state machine in this first verifier.

This boundary is deliberate: byte, schema, cryptographic, and contextual
artifact agreement is the cross-language gate. Stateful runtime behavior
remains covered by the existing abstract Python scenario harness until a second
runtime implementation is separately authorized.

## Data flow

The CLI performs these steps in order:

1. resolve and validate the vector root;
2. parse and validate `manifest.json`;
3. enumerate package artifacts and reject package drift;
4. verify every artifact length and SHA-256;
5. structurally decode or reject each artifact as specified;
6. re-encode every accepted CBOR or COSE structure byte-for-byte;
7. verify COSE Sign1 and Route Open proof inputs;
8. apply the portable semantic checks;
9. compare actual and expected outcome/error for every artifact; and
10. emit a bounded summary and return exit code 0 only on complete agreement.

The CLI prints vector IDs and concise results. It never prints seeds, complete
COSE objects, proof signatures, raw artifacts, Origin Endpoints, or other
potentially sensitive byte content.

## Failure behavior

Every failure is local and fail-closed:

- malformed CLI arguments or unsafe paths return nonzero before artifact reads;
- manifest ambiguity or package drift returns nonzero;
- one vector mismatch makes the complete verification fail;
- an unexpected exception is reported as a bounded verifier-internal failure,
  not converted into an NBSR protocol error;
- verification never rewrites or repairs the package; and
- no network, DNS, clock, or environment-specific policy source is consulted.

The fixed fixture time used for expiry checks comes from the approved vector
contract, not the wall clock. The verifier declares the literal validation time
`1893456000` independently; it does not import the Python fixture module.

## Testing

Node's built-in test runner will cover:

- strict manifest schema, enum, ordering, and path rejection;
- missing, extra, modified, and path-escaping artifacts;
- SHA-256 and length mismatches;
- all supported deterministic CBOR types;
- every structural invalid vector;
- the different-length map-key ordering case;
- accepted byte-for-byte decode/re-encode;
- valid and invalid COSE Sign1;
- valid and invalid Route Open proof;
- boolean-as-integer rejection;
- grant expiry and port authorization;
- version mismatch and generic close;
- exact outcome/error equality for all 32 artifacts; and
- successful read-only verification of the checked-in package.

Repository documentation tests will require:

- Node verifier isolation from `nbsr/` runtime;
- no npm dependencies or lifecycle scripts;
- no use of test seeds;
- no package writes;
- exact current vector coverage; and
- an honest statement that vector agreement is not production readiness.

Final validation will run the Node tests and CLI first, followed by the focused
Python vector suite, full Python suite, Ruff checks, `pip check`, deterministic
regeneration check, and `git diff --check`.

## Explicit exclusions

This task does not:

- add Go, Rust, .NET, QUIC, TLS, DNS, proxy, or cloud dependencies;
- implement sockets, Transport Sessions, Service Channels, or Application
  Streams;
- create or modify any wire message, numeric key, error code, state,
  transition, critical extension, or COSE wrapper;
- implement multi-channel, migration, resumption, or handover behavior;
- modify frozen Core v0.1 decisions D1-D6;
- change the Python-generated vector bytes;
- begin WP3 runtime integration; or
- make a production-readiness claim.

## Acceptance criteria

The design is implemented successfully only when:

- the verifier is Node.js-only and dependency-free;
- it reads but cannot rewrite the vector package;
- all 32 current artifacts reproduce their exact expected outcomes;
- accepted deterministic CBOR re-encodes identically;
- COSE Sign1 and proof signatures verify independently;
- all Node and existing Python validation passes;
- the checked-in vector package remains byte-identical;
- frozen registries and schemas remain unchanged; and
- the repository describes this as cross-language vector agreement, not a
  second runtime or production implementation.
